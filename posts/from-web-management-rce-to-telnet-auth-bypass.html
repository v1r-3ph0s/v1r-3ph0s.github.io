From Web Management RCE to Telnet Auth Bypass: An Embedded Device Walkthrough

📅 Mar 05, 2026 ⏱ 30 min read
#rce #command-injection #iot #telnet #pentest

Embedded systems and IoT network appliances frequently manage critical network boundaries, yet their internal firmware often relies on legacy design patterns and precarious assumptions about client-side trust. During a targeted security assessment of an embedded gateway IoT device in an isolated lab environment, I uncovered a complete chain of vulnerabilities leading from open web directory indexing down to an unauthenticated Remote Code Execution (RCE) primitive, ultimately enabling an unrestricted Telnet authentication bypass and a full root shell.

In this walkthrough, I will take you step-by-step through my entire research and exploitation workflow: from initial port enumeration and client-side source code analysis, through CGI request reconstruction and command filter evasion, to rewriting the device's system authentication database to spawn a root shell on the diagnostic Telnet daemon.

⚠️ Educational Disclaimer: All testing, demonstrations, and commands discussed in this post were conducted in a strictly controlled laboratory environment on hardware dedicated to security research. Target identifiers, device models, and vendor names have been completely sanitized for educational and demonstration purposes. Never perform security testing against devices or networks without prior written authorization.

1. Initial Reconnaissance & Port Enumeration

I began my assessment with standard network mapping against the gateway's management interface at 192.168.1.1. To ensure no non-standard management ports or hidden debugging services were missed, I performed a full TCP port scan across all 65,535 ports using nmap.

The port scan immediately highlighted three notable attack surfaces:

  • Port 80 (HTTP): Hosted the primary web-based administrative portal used by administrators to configure network parameters, APNs, routing, and system maintenance.
  • Port 22 (SSH): Was in a filtered state, indicating network-layer firewall rules restricted SSH access.
  • Port 4719 (Telnet): An obscure, non-standard high port running a live Telnet daemon.

When I established a direct Telnet connection to port 4719, the daemon prompted for a username and password. Brute-forcing this login was neither practical nor stealthy, but having an active command-line daemon listening on the device meant that if I could manipulate the underlying operating system's credentials, port 4719 would become an immediate interactive entry point.

3. Client-Side Source Analysis & Hidden Handler Discovery

I downloaded main.js and began reviewing how the frontend UI communicated with the backend firmware. In modern web applications, client frameworks abstract API requests; in embedded IoT devices, developers frequently define an enumeration of integer commands and map them to CGI endpoints.

Searching for configuration and execution keywords in main.js, I spotted a notable list of command definitions:

// Snippet from exposed /js/main.js
TU_CONFIG: 41,
WG_CONFIG: 42,

DEVICE_VERSION_INFO: 43,

LOG_CONFIG: 44,

AT: 45,

EXE_CMD: 46,
SYSLOG_FUNCTION_CONFIG: 47,

A variable explicitly named EXE_CMD assigned the numeric opcode 46 strongly suggested command execution capability built directly into the firmware's management layer.

Pivoting deeper into main.js to find where EXE_CMD was referenced, I uncovered the corresponding route handler table:

// Dispatcher mapping table in /js/main.js
ADVANCED_CONFIG: { cmd: RequestCmd.BASIC_CONFIG, url: "html/advance/advancedConfig.html" },
ROUTER_TABLE: { cmd: RequestCmd.ROUTER_TABLE, url: "html/route/routeIndex.html" },

The handler SYSTEM_MANAGE coupled opcode EXE_CMD (46) with a template located at html/manage/systemManage.html. When I inspected that template file, I found a hidden administrative diagnostics form:

5. Filter Evasion via Command Chaining

When testing known diagnostic utilities against the endpoint, I noticed that the ps (process status) command was accepted and executed without issue:

Notice two vital details revealed in this response:

  1. The processes, including system init, were executing under user context admin (UID 0 / root equivalence on this system).
  2. The backend was likely taking the string value of requestCmd and passing it to a shell interpreter (such as /bin/sh -c) rather than executing an isolated binary via execve.

If the input was passed to a shell without strict sanitization, shell metacharacters could allow me to chain secondary commands after the whitelisted ps binary. I tested Unix pipes (|) to feed the output of ps into arbitrary shell commands.

I submitted the chained payload "requestCmd": "ps | ls /":

The filter check was completely bypassed. The server validated that the input began with or contained the allowed keyword ps, but because it concatenated the entire string into a shell invocation, the pipe operator passed control directly to my secondary command. I had achieved arbitrary Remote Code Execution (RCE).

6. Telnet Authentication Bypass via /etc/passwd Manipulation

While I had RCE over HTTP POST requests, interacting through individual JSON payloads is cumbersome for thorough firmware analysis and network-level testing. I wanted an interactive root shell. Recalling that port 4719 was running Telnet with password authentication, I decided to use my RCE primitive to inspect and modify the IoT device's authentication database.

Step A: Inspecting /etc/passwd

I used the chained command ps | cat /etc/passwd to read the device user definitions:

# Payload sent in requestCmd:
ps | cat /etc/passwd

# Response received:
admin:R0.kqzgRjrZUU:0:0:root:/:/bin/sh

The admin user had a UID and GID of 0:0 (root privileges), but possessed an encrypted password hash in the second field (R0.kqzgRjrZUU), which was an old DES-based salt/hash format. Attempting to crack this hash offline was unnecessary because my RCE was running with root privileges, meaning I had write permissions to the filesystem.

Step B: Replacing /etc/passwd

In Unix-like systems, if the password field in /etc/passwd is empty (i.e., admin::0:0:root:/:/bin/sh), the system considers the account to have no password set and will permit immediate login without prompting for credentials.

I executed the following two steps to overwrite the authentication entry:

# 1. Remove the existing password file
ps | rm -rf /etc/passwd

# 2. Re-create /etc/passwd with a passwordless root entry
ps | echo admin::0:0:root:/:/bin/sh >> /etc/passwd

Both commands returned HTTP 200 without error. The IoT device's user database had been rewritten to accept admin with an empty password hash.

9. Defensive Remediation & Hardening

Securing embedded systems against this attack chain requires addressing each layer of the vulnerability stack:

1. Eliminate Shell Invocations in Backend Daemons

Never construct shell commands using string concatenation. If external binaries must be called, use parameterized system calls (such as execve() or POSIX posix_spawn()) where arguments are passed as discrete array elements rather than interpreted by /bin/sh.

// Vulnerable pattern:
char buffer[512];
snprintf(buffer, sizeof(buffer), "ps %s", user_input);
system(buffer); // Shell interprets pipes, semicolons, and backticks!

// Hardened approach:
// Use strict parameterization and do not invoke a shell wrapper.
char *args[] = { "/bin/ps", NULL };
execve("/bin/ps", args, environ);

2. Enforce Least Privilege on Daemons

Web servers and CGI handlers should never execute with UID 0 (root). Running the web service under a dedicated unprivileged user (e.g. www-data) ensures that even if command execution occurs, attackers cannot modify system files like /etc/passwd or reconfigure core networking daemons.

3. Disable Web Server Directory Indexing

Configure the web server to prohibit directory browsing. For mini_httpd or similar embedded servers, disable the directory listing option during compilation or pass appropriate command-line flags (such as -d or restricting directory index listings in custom builds).

4. Retire Telnet & Restrict Debugging Interfaces

Telnet transmits credentials and traffic in plaintext and represents an outdated diagnostic interface. In production firmware:

  • Disable all Telnet daemons by default.
  • Replace remote administrative access with SSH enforcing key-based authentication.
  • Ensure diagnostic interfaces used during hardware manufacturing or QA testing are completely stripped prior to shipping production firmware.

10. Conclusion

This engagement demonstrated how quickly an embedded device can be compromised when security relies on client-side obscurity and superficial command filtering. An open directory listing revealed internal API constants; an unauthenticated CGI dispatcher accepted shell metacharacters; and running the web server as root allowed rewriting the authentication database to unlock a forgotten Telnet interface.

By treating all input as hostile, executing helper binaries without shell wrappers, and running web daemons under least-privilege principles, embedded device manufacturers can effectively break each link in this exploit chain and safeguard network gateways against takeover.
